# 安装后重新打开时的后台连接修复

## 根因与改动

用户报告重新打开 WinOne 时提示 `无法连接后台：open \\.\pipe\WinOne-… The system cannot find the file specified. (transport)`。本轮在仓库内用旧正式程序、真实命名管道预约和独立配置复现了相同窗口错误，没有改动真实安装或配置。

确认了两个启动顺序缺陷：

1. `apps/desktop-mygo/app/run_windows.go` 的 `ensureHost()` 把暂时存在但不能服务的通道转入连接等待。如果预约随后释放，原循环只继续连接已经不存在的通道，不再进入后台启动路径。旧实现的真实后台回归约 13.14 秒后失败。安装维护程序的预约来自 `internal/installguard/session_windows.go`，它在持有维护锁时创建通道，结束时关闭通道。
2. 主页面已经等待首次后台状态，插件布局和根窗口插件轮询却在首帧发送后台请求。因此，即使后台随后启动成功，窗口仍可能保留早期的缺失通道通知。修复第一处后，真实窗口验证揭示了这一问题。

现在等待循环会重新检查通道。通道不存在时，先复用客户端的进程退出判断，再进入既有后台启动路径。窗口取消后不启动后台；已有客户端观察到后台退出码 0 时仍拒绝自动重启。插件布局、导航和轮询与普通页面共用首次后台状态边界。真实启动失败仍显示错误和“重试连接”，没有增加生产延时、放宽超时或隐藏失败。

## 可复现检查

- `build/test-host-startup.ps1 -OutputDirectory _temp/<任务>/startup -GoExe <MyGo 编译器> -HostGoExe <Host 编译器>`：显式选择真实后台启动检查。运行器创建私有桌面和独立配置，禁用系统模块；默认测试不启动后台或托盘。
- `apps/desktop-mygo/app/host_startup_windows_test.go`：通道缺失、预约释放、重复打开复用同一后台 PID，以及退出码 0 后旧客户端不自动复活。退出码检查使用测试自建进程，不等同于点击真实托盘菜单。
- `apps/desktop-mygo/shell/startup_test.go`：通过真实通道测试首次后台状态之前不发送插件请求，状态到达后仍加载插件；实际启动失败保留错误和重新连接操作。

原始失败、修复后的结果及实窗记录保留在 `dist/reports/backend-reopen-20261111/`。记录只适用于对应源码和程序摘要，不作为冷缓存或 P95 性能承诺。

## 交付边界

正式安装器继续使用 `dist/release/WinOne-setup.exe`。最终隔离安装、覆盖、配置保留、启动及卸载验证完成后，才替换该文件并同步 SHA-256、配套卸载器和 `release-info.json`。旧正式包保留在本轮 `_temp/` 备份目录。最终摘要和安装器来源以 `release-info.json` 为准。

本轮不安装或更新用户的真实 WinOne，不修改真实自启、系统权限或其他软件；不创建远端仓库、tag 或公开发布。
