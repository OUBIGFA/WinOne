# 桌面启动分段诊断

更新：2026-10-07。**启动预算仍未通过；本次诊断未修改产品窗口行为。**

## 当前四模块包复测（2026-10-07）

图标修复包 `icon-quality-20261007` 使用独立配置完成 21 次可见窗口启动。第 1 次新配置启动为 604.96ms；后 20 次同配置重开为 542.25–613.69ms，最近秩 P95 为 **587.78ms**。`-EnforceWarmBudget` 按原 300ms 门槛返回失败。新配置不等于操作系统冷缓存；计时终点仍为首页数据与控件就绪，不是实际显示或输入延迟。

| 后 20 次的阶段 | 耗时范围 |
| --- | --- |
| 原生窗口就绪至 WebView 创建完成 | 369.12–425.86ms |
| WebView 创建完成至首页就绪 | 142.16–164.73ms |

Host 初始化仍与 WebView 创建并行。21 次各记录 6 个 WebView2 进程，正常关闭后均回收，最长 4.08 秒。此次未改产品实现，且运行时已为 WebView2 155.0.4283.39；不能把与此前 1025.18ms 的差值归因于代码优化。

首次 21 次尝试在第 11 次退出检查失败，进程计数由 6 增至 12。原测量脚本仅用父 PID 扩展进程树，没有检查子进程是否早于父进程创建。受控用例注入一个旧父 PID 关联及其后代，复现了无关进程被计入、退出检查失败。脚本现复用 `resource-metrics.psm1` 的创建时间校验；同一用例先失败后通过，保留逐次进程身份及退出时的剩余身份。原失败没有记录具体身份，因此不能断言这已证明第 11 次的全部原因。修复不改变产品关闭行为或验收门槛。

另采集两次独立 Chromium 诊断记录。渲染线程中最大 React 调度回调分别为 52.80/51.65ms，另一个较大回调为 36.82/39.79ms；单次最大布局事件为 33.63/33.82ms。回调包含嵌套布局等工作，不能相加；未记录到某种脚本事件也不代表该开销为零。首页入口确实静态导入其他设置页，但当前记录不足以证明拆包能减少多少启动时间。未据此更改页面加载流程；仅缩减首页代码也无法消除超过总预算的 WebView 创建阶段。

可复现回归：`tests/resource-metrics/component-startup.tests.ps1 -BundleDirectory <完整包> -OutputDirectory _temp/<新目录>`。此测试显式启动隔离窗口，用合成清单验证父 PID 复用，不操作用户程序。正式性能入口为 `build/benchmark-component-startup.ps1 -BundleDirectory <完整包> -OutputDirectory _temp/<新目录> -Runs 21 -EnforceWarmBudget`。完整记录（包括失败、原始跟踪及脚本）在 `_temp/repository-hygiene-20261008-9513b969/archived-dist/startup-diagnostics-20261007/`。

进程归属依据：[Microsoft Win32_Process](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-process) 的 ParentProcessId 与 CreationDate 说明。后续先定位首页调度回调中的实际组件工作，再做同包对照；若仍受 WebView 创建成本限制，需要重新评估宿主方案，同时保留既有 UI、输入法与图形能力。

## 首页首次布局对照（2026-10-07，未采用）

通过仅用于诊断的 Rust 源码副本，在初始化脚本中记录尺寸读取及滚动写入。两次首次文档中，`AppShell` 挂载时的 `scrollTop = 0` 分别触发 34.40/36.90ms 同步布局；后续 `react-resizable-panels` 注册面板时的 `offsetLeft` 读取分别触发 19.80/21.10ms 布局。记录保留调用栈。同一窗口重载时的面板读取只有 3.40/3.70ms，不能用重载代替新窗口首次布局证据。Chromium 启动类别未提供调用栈/CPU Profile，缺失不当作零开销。

候选只跳过首次挂载的滚动写入，切页仍回到顶部。新增回归先失败后通过，连同首页、导航及启动探针共 33 项通过；候选由统一构建脚本生成。相邻两组各启动 7 次，首个新配置样本单独保留，后 6 次如下：

| 指标 | 原包 | 候选 |
| --- | ---: | ---: |
| 完整启动平均值 | 558.68ms | 582.02ms |
| WebView 创建后至首页就绪平均值 | 147.54ms | 150.75ms |

候选包含一次 WebView 创建较慢的样本，没有将其丢弃；即便单独观察页面阶段，也没有得到收益证据。该样本量不用于正式 P95 验收，也不能证明所有设备都无差异。**不采用这次改动**，已撤回候选源码和专属测试；重新构建的前端资产与实验前逐文件一致。日常试用版未替换，前述 587.78ms 正式基线继续有效。

方法参考：[web.dev：避免大型复杂布局和布局抖动](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing)。同步布局是定位线索，减少一次调用不等于减少整个任务的布局成本。实验、回归结果摘要、调用栈及构建记录在 `_temp/repository-hygiene-20261008-9513b969/archived-dist/home-layout-20261007/`。暂不继续在同一方案上叠加补丁，下一项本地工作转为补齐可选模块安装与运行的缺失连接。

## 此前确认的等待（2026-10-06）

同一份现有 UI、Wry 0.57.0、WebView2 155.0.4283.33，使用独立配置和可见窗口。诊断副本只增加阶段日志，产品源码、锁文件和依赖缓存保持原样。7 次启动中，后 6 次的结果如下：

| 阶段 | 耗时范围 | 平均耗时 |
| --- | --- | --- |
| WebView2 环境创建 | 7.69–8.34ms | 7.97ms |
| WebView2 控制器创建 | 503.63–535.37ms | 522.37ms |
| 事件及消息接口初始化 | 45.36–61.50ms | 49.99ms |
| 脚本注册后的显示与焦点初始化 | 74.17–145.70ms | 108.63ms |

主要等待发生在控制器创建期间。不能将这段时间归因于首页组件或设置读取，也不能将环境对象创建时间当成整个 WebView2 启动时间。
