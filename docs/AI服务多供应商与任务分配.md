# AI服务多供应商与任务分配

状态：2026-10-06，配置、任务路由、窗口临时切换和账号隔离已接入并通过针对性验证，已更新日常试用版。

## 用户得到的行为

- 独立 AI服务页管理多个自定义供应商或独立账号，标签依次为自定义供应商、账号供应商、默认 AI 服务。每项有名称、协议/登录类型及多个模型。
- 获取模型使用当前地址、协议、预设、密钥或账号，不要求先保存。发现的模型保留在表单中，勾选后可用于任务；只有保存才持久写入配置和密钥。手动填写模型继续保留。
- 默认模型与 OCR、翻译、结果对话分别选择供应商和模型。OCR 的本地识别、Google 翻译继续保留；后续模块可使用默认模型。
- 结果窗的输入区可临时选择已配置的供应商及模型。选择作用于该窗口后续识别、翻译和对话请求，不改全局任务分配，不重发已有请求。清空临时选择恢复按任务调用。
- 每条模型回复保留实际请求所选模型名称；重试失败保留旧回复。
- 划词 AI 功能只用 AI服务，动作独立选择优先，否则使用全局 default；未配置时明确报错，不沿用 Google 或截图/对话的其他任务分配。划词结果显示实际供应商和模型，截图结果区不显示这些名称。

## 配置与调用边界

使用稳定供应商 ID 关联密钥、账号目录、模型列表和任务选择。功能模块调用时只传 ID/模型，不另存 API 地址或凭据。Host 在启动每次请求时校验选择并取得不可变快照；已有请求不会因设置修改而换用另一个密钥。

AI服务设置页的 `ai.models.fetch` 另外接受临时 `connection`（protocol、baseUrl、preset、presetRegion、keys、keyPolicy）及逐输入项 `keyUpdates`。地址、输入项身份、重复密钥和策略复用保存校验；只解析选中供应商，不要求其他未完成表单先保存。临时凭据快照复用多密钥失败切换，不写配置文件，也不改变正式请求的轮询/冷却状态。账号草稿继续使用 `draft`，与自定义连接互斥；旧的仅 provider ID 请求继续可用。

现有单一配置在读取新设置时呈现为一项“现有服务”，首次保存新配置时原子写入新版结构；原密钥复用其 DPAPI 密文，不要求重新填写。旧智能体使用原有隔离目录；新增账号使用各自隔离目录，同一智能体的两个账号互不切换。旧配置入口在新版多服务配置保存后只供读取，拒绝可能覆盖新版信息的旧式写入。

不采用为每个模块保存供应商配置的方案，因为会重复凭据并使默认任务分配失效。也不把新账号都写入同一个 magpie 用户目录，因为那会使同一智能体的登录互相覆盖。

## 依据与证据范围

本轮验证包括：旧密钥迁移与重读、逐服务密钥、任务覆盖及默认回退、无效模型拒绝、超大配置拒绝保存、旧版本可读配置投影；真实 magpie 从两个独立账号目录仅读到各自的模拟账号。实际 Host 和结果窗通过两个回环服务验证 OCR、翻译、对话分别使用指定模型；窗口临时切换同时改变地址、模型和密钥，历史回复标签及全局任务配置保持不变。设置页的服务、账号、任务分配在中英、深浅色、520/800/1280 宽度检查通过。账号验证使用测试数据，未登录用户真实账号。

- magpie 固定提交 `8c71cd27f95432362b91fe140bbffacc550def8b` 的 `internal/provider/logins.go`、`account.go` 与既有 WinOne `internal/ai/process_windows.go`：账号发现和登录使用用户/配置目录，WinOne 已隔离这些路径。本阶段在该边界增加独立账号目录。
- 已有 `internal/ai/store_windows.go` 的 DPAPI、原子保存与 revision 检查继续作为凭据和冲突处理基础。
- 实现与模拟登录测试不证明真实账号已登录；供应商实际可用模型由用户账号权限决定，不伪造或静默替换。
