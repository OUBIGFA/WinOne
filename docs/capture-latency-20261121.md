# 截图与 OCR 响应（2026-11-21）

目标：按下截图或 OCR 快捷键后立即可用。本次处理四个使用中的等待来源，并为大选区 OCR 接入显卡推理。真实安装和用户配置不在本次自动操作范围内。

## 原因

按下快捷键到截图窗口出现的常规路径不慢：本机读取 3440×1440 桌面 36–49 ms，枚举 453 个顶层窗口约 1 ms，窗口首帧约 58 ms（11-13 的 100 次样本）。慢出在下列环节：

| 现象 | 原因 | 位置 |
| --- | --- | --- |
| 完成或取消截图后，窗口迟迟不关 | 每次截图都把整屏原图编码为 PNG 草稿。关闭时等这次编码结束；画面复杂时编码 0.65–0.95 s（普通界面约 0.1 s） | `NativeCaptureAutosave.FinishCoreAsync` |
| 收尾期间再按快捷键没有反应 | Host 同时只执行一个快捷键操作，忙时的按键直接丢弃；任务结束靠 250 ms 轮询发现 | `shortcutRuntime.run`、`waitCaptureJob` |
| Shift+C 时有时无反馈 | 识别期间截图窗口隐藏，没有任何提示；同时占着 Host 的忙状态 | `NativeRecognitionSession` |
| 小选区 OCR 有时要两三百毫秒 | Windows 对后台进程启用 EcoQoS（效率核、低频）。Python OCR 进程从未退出该策略；单行选区节流时约 230 ms，全速约 16 ms。截图进程已在用户操作时退出节流，OCR 进程没有 | `recognize.py` |
| 大选区 OCR 很慢 | CPU 推理随文字量增长：12 行约 0.5 s，30 行约 2 s，满屏 45 行 6.3–8.8 s。批量、并行、加线程都不更快 | `recognize.py` |
| 事后无法定位某次慢在哪 | 没有分段耗时；快捷键失败只写入设置页状态 | — |

## 修改

1. **先关窗，后清理。** 丢弃草稿时，先持久记录“已作废”（恢复不再显示它，下一次截图可以立即建立新草稿），随即关闭窗口并结束任务。原图编码和文件清理作为后台任务继续，截图进程退出时在原有 8 秒退出期限内等待它们；新截图不等待。
2. **Host 不丢按键。** `capture.jobs.get` 支持 `waitMs`（上限 2 s）：截图进程在任务结束时立即答复，Host 不再固定轮询。截图进行中再按快捷键：先激活当前截图窗口；没有可激活的窗口时保留最后一次按键，当前操作结束后立即执行。置顶快捷键改为独立执行，不等截图。
3. **耗时与失败日志。** 每次快捷键操作在 `%LOCALAPPDATA%\WinOne\logs\host.log` 写一行 `shortcut.timing`：排队、总耗时，以及截图进程的阶段（主题、取帧、窗口创建、显示、关闭、结束）。失败写 `shortcut.failed`。本地 OCR 每次识别写 `ocr.timing`（设备、图片尺寸、字节、耗时），每个 OCR 进程首次就绪写 `ocr.ready`。日志不含图片或识别文字。
4. **Shift+C 状态提示。** 选区下方显示不抢焦点、不拦截鼠标的小提示：识别超过 150 ms 时显示“正在识别…”，复制后显示“已复制识别结果”约 1.2 秒。失败时恢复截图并显示错误，提示关闭。新截图取帧前先关闭提示，避免把它截进画面。配色、圆角和字体取自工具栏的共享样式。
5. **OCR 识别时全速运行。** 每次用户识别期间，OCR 进程按 Windows 服务质量接口关闭执行速度节流，结束后恢复原策略；待命维护仍按系统策略省电。做法与截图进程现有的 `InteractiveWorkScope` 相同。
6. **大选区使用显卡。** 见下一节。

## OCR 显卡推理

采用 DirectML（`onnxruntime-directml` 1.21.1，MIT，wheel 约 24 MB，内含 DirectML 1.15.4）。它支持任何 DirectX 12 显卡，并自带 CPU 执行器。CUDA 版只支持 NVIDIA 且需额外约 1 GB 运行库，未采用。

DirectML 会话会按最大输入缓存中间缓冲区：创建后 OCR 进程提交内存约 0.9 GB，识别一次满屏后约 5.5 GB，会话存续期间不回落。按用户选择采用“按需显卡”：

- 常驻的仍是 CPU 引擎。小于 100 万像素的选区始终用 CPU（单行约 20 ms）。
- 不小于 100 万像素时，临时创建两个 DirectML 会话（并行创建，约 0.3–0.4 s），识别后立即释放。引擎外壳在待命准备时建好，不占显卡内存。
- 显卡识别时每批 6 行；CPU 保持每次 1 行（CPU 上批量更慢）。关闭 DirectML 元命令后，本机 NVIDIA 驱动上快约 2 倍。
- 显卡不可用或出错时，该 OCR 进程改用 CPU 并重试本次请求；Host 启动的下一个 OCR 进程会再尝试显卡。`WINONE_OCR_DEVICE=cpu` 强制 CPU。

准确率：5 页生成文字（24,322 字）的字符错误率，CPU 0.51%，显卡批量 6 行 0.49%。批量识别会让少数行的结果与 CPU 不同（约 0.05% 字符），已按原文核对不是变差。

## 测量

环境：i7-12700K（20 线程）、64 GB、RTX 3080 Ti、单屏 3440×1440。早期几轮测量的 CPU 数值偏高且波动，原因正是上面的 EcoQoS 节流（当时误判为后台负载）；下表 OCR 数据在加入全速运行后重测，同一表内各项交替运行。

实际 Host、截图和 OCR 进程组（私有桌面，`OcrHostLatencyProbe`，生成的 260×65 `Hello 123`，原生 Shift+C 会话）：

| 条件 | 选区提交到复制回调（11-13） | 本次 |
| --- | ---: | ---: |
| 连续使用 | 288.86–353.26 ms | 23.9–26.7 ms |
| 闲置后第一次 | 458.90 ms（600 s） | 26.2 ms（65 s） |

其中识别约 17–20 ms。复制回调为测试接收器，不等于真实系统剪贴板写入时间。

截图关闭到任务结束（私有桌面，生产草稿自动保存，噪声画面，`NativeCaptureLatencyProbe`）：

| 版本 | 关闭到返回 | 首帧 |
| --- | ---: | ---: |
| 修改前 | 376–456 ms | 69–76 ms |
| 修改后 | 22–31 ms（首次 65 ms） | 75–106 ms |

修改后首帧略高：上一张被丢弃的原图仍在后台编码，与下一次截图争用 CPU。最后一张的后台编码在 378 ms 内完成并清理。

OCR 工作进程（产品 `recognize.py`，帧协议，生成图片，各 5 轮中位数）：

| 选区 | 纯 CPU | 按需显卡 |
| --- | ---: | ---: |
| 260×65，1 行 | 17 ms | 20 ms（CPU） |
| 900×500，12 行 | 468 ms | 478 ms（CPU） |
| 1200×840，20 行 | 961 ms | 867 ms（显卡） |
| 1600×1000，30 行 | 2,006 ms | 988 ms（显卡） |
| 3440×1440，45 行 | 6,618 ms | 2,200 ms（显卡） |

显卡时间包含创建两个 DirectML 会话（约 0.3–0.4 s）。OCR 进程提交内存：待命约 108 MB；上述全部识别后约 233 MB（纯 CPU 进程 289 MB），显卡会话已释放。

## 验证入口

- `tests/capture-host-probe/NativeAutosaveTests.cs`：丢弃不等编码、后台编码期间可建立新草稿、退出前编码完成并清理。
- `apps/host/hotkeys_windows_test.go`：完成立即被发现（无 250 ms 轮询）、忙时保留最后一次按键。
- `tests/capture-host-probe/NativeTextRecognitionTests.cs`：静默 OCR 显示“正在识别”和“已复制”，失败不留提示。`--native-text-status-render`（`test-capture-native.ps1 -Suites text-status`）渲染中英、深浅色提示。
- `internal/ai/ocr_worker_windows_test.go`：`ocr.ready` 每进程一次、`ocr.timing` 不含文字、PNG 尺寸读取。
- `tests/ocr/test_recognize.py`：识别期间关闭执行速度节流并恢复原策略；设置 `WINONE_OCR_RUNTIME`（可选 `WINONE_OCR_EXPECT_DEVICE=gpu`）后，小选区用 CPU、大页面用显卡且与 CPU 读出相同文字。用系统 Python（需要 Pillow）运行：`python -m unittest tests.ocr.test_recognize`。

## 未覆盖

- 物理快捷键到屏幕显示的整段时间、真实系统剪贴板、休眠唤醒后的显卡设备恢复。
- AMD、Intel 显卡及无 DirectX 12 设备的机器（代码路径为改用 CPU，未在这些硬件上实测）。
- 长时间运行的内存曲线。
