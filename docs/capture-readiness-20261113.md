# 安装包体积与截图、OCR 待命（2026-11-13）

本次处理安装包体积、长时间闲置后截图与 Shift+C 识别复制的等待，以及“移动标注”的工具栏分组。保留全部现有功能、离线 OCR 模型、完整对应源码和原始许可证。真实安装和用户配置不在本次自动操作范围内。

## 原因与取舍

原正式安装器为 335,957,242 字节（320.39 MiB）。未压缩载荷中，OCR 运行时约 181.15 MiB，Anki 约 135.29 MiB，共享 AI 运行时约 128.82 MiB。Bun 是账号服务的运行依赖；ShareX.HelpersLib 使用 WPF，不能直接移除 WPF 运行库。

Anki 的 630 份第三方对应源码原来各自采用 gzip 压缩，外层再套 ZIP。安装器无法有效合并已经压缩的内容。改为先校验每个原始归档，再完整保留解压后的 tar 字节，最后用一个 XZ 流统一压缩。内层源码、许可证、构建资料、权限和链接记录均保留；`SOURCES.json` 同时记录原始归档和 tar 的 SHA-256。

| 对象 | 修改前（字节） | 修改后（字节） |
| --- | ---: | ---: |
| Anki 完整第三方源码归档 | 96,267,248 | 46,295,132 |
| 正式安装器 | 335,957,242 | 256,524,863 |

最终安装器由 320.39 MiB 降至 244.64 MiB，减少 75.75 MiB（23.64%）。剩余体积仍主要来自随包提供的离线 OCR、AI 和原生运行环境。新载荷中，OCR 为 181.15 MiB，AI 为 128.82 MiB，Anki 为 87.63 MiB；这些是未压缩目录大小，不能直接相加当作安装器大小。

新归档 SHA-256：`5dc836f1dd0329bd3a53b94b8fe639adb41ad2bfe04e9a189359ba8034086bbf`。生成器验证全部原始输入；运行时检查同时核对锁定的归档摘要、630 项内容和 1,116 份原始许可记录。正式 Go 后台程序及安装辅助程序去掉调试器符号，保留运行诊断和构建身份。正式安装器的 LZMA 字典改为 32 MiB；该内存开销只发生在安装时。

截图进程和本地 OCR 原本已经常驻，不能把“新增常驻”作为此次改进。旧实现只在启动、恢复和解锁时准备热点代码及模型；普通长时间闲置没有维护，异常或取消导致 OCR 进程结束后，需要下一次识别重新创建模型。现有任务等待使用完成信号，没有另外增加固定轮询等待。

原包隔离测量中，OCR 首次准备约 10,967 ms，准备后识别生成的 `Hello 123` 为 230–321 ms，闲置 65 秒后为 233.78 ms。截图未预热首帧约 449 ms，预热后约 67–73 ms。这些数据说明初始化成本较大，但 **65 秒闲置没有复现用户报告的长等待**。该轮测量末尾的私有桌面托盘退出未通过，不能将它写为完整验收通过。

进一步测试实际模块开关时，复现了独立的待命缺口：关闭再启用截图后，本地 OCR 持续不就绪，整轮测试达到 210 秒上限时仍未恢复。`IntentChanged` 在配置事务尚未结束时调用待命检查；此时恢复保护正确地返回“尚未完成”，却把 OCR 待命开关和维护计时器一起关闭。事务完成后没有再次同步。下一次识别仍可临时启动解释器，但已关闭的待命状态会使它在识别后再次退出。

本次在 `HostStore` 的配置提交、回退和恢复结束处增加只负责同步后台意图的通知。Host 在最终配置状态确定后重新检查待命。恢复仍未完成时保持关闭；通知本身不等待模型加载、不启动新的配置事务。配置回归覆盖成功提交、成功回退、回退失败及显式恢复，实际进程测试覆盖模块关闭和重新启用。

## 当前实现

- Host 复用一个 30 秒维护计时器，准备已启用的原生截图入口及本地 OCR。计时器在本轮准备完成后重新计时，休眠后不补跑积压任务。
- 截图正在编辑或最近 30 秒已经活动时跳过截图维护。准备只使用生成的图片，不读取屏幕、不显示截图窗口、不写入用户图片。
- OCR 复用同一个 Python 进程和两个模型会话。识别忙时，维护直接跳过；不会排在用户识别后再次运行。已经就绪的解释器意外退出时，现有退出通知立即触发后台恢复。30 秒内再次失败时交给维护计时器，避免连续启动循环；禁用模块或退出 Host 不触发恢复。
- 禁用截图模块时停止维护并释放相关进程；选择 AI OCR 时释放本地模型。配置事务结束后重新确认待命，选择本地 OCR 及系统恢复/解锁沿用现有准备入口。设置窗口不因此常驻。
- “移动标注”位于标注组开头，即矩形、椭圆和箭头之前；命令仍使用原来的 `select`，保留单个标注移动、撤销、重做和自定义工具可见性。

## 实际进程与闲置测量

`idle-600/host-latency.json` 已完成整轮验证，使用生成的 260 × 65 像素短文本 `Hello 123`。它是一次受控样本，不是所有图片或物理快捷键的 P95 承诺。

| 条件 | 选区提交到复制回调 | 其中识别与 Host 通道 |
| --- | ---: | ---: |
| 连续使用，4 次 | 288.86–353.26 ms | 283.33–346.14 ms |
| 闲置 600.04 秒后的第一次 | 458.90 ms | 453.28 ms |
| 只回收本轮自有进程工作集后的第一次 | 780.64 ms | 774.39 ms |
| 切回本地 OCR 后 | 360.29 ms | 352.58 ms |
| 关闭再启用截图模块后 | 325.17 ms | 316.68 ms |

闲置后的会话首帧为 150.59 ms，从会话创建到复制回调为 610.20 ms。复制回调只是本轮隔离接收器，不等于实际系统剪贴板写入时间。工作集回收也不等于清空系统文件缓存或真实休眠。

闲置期间，截图准备次数从 1 增到 20，OCR 始终使用同一个进程。原有三进程组的私有提交内存由 177.60 MiB 变为 193.89 MiB，增加 16.29 MiB；结束时 Host、截图和 OCR 分别约 54.00、36.62、103.28 MiB。没有新增常驻进程。600.04 秒内累计 CPU 时间为 20.17 秒，按本机 20 个逻辑处理器折算，平均约占整机 CPU 容量的 0.17%（单核口径约 3.36%）。这只是该轮受控测试的平均值。

10 分钟测量时，故障恢复还依赖下一次维护，实际等待 32.28 秒。针对这段等待，随后改为退出事件立即触发恢复。首次复验为 1,334.28 ms；最终干净构建的 `ocr-release.json` 再次复验，异常退出到重新就绪为 3,059.54 ms，恢复后从选区提交到复制回调为 300.47 ms，正常连续使用为 212.61–268.34 ms。机器负载与缓存状态不同，不能把轮次间的识别耗时差异归因于退出恢复改动，也不以短测替代前面的闲置测量。

最终构建同样覆盖切换 AI OCR、关闭模块及重新启用：相关本地进程按预期释放；关闭模块后继续等待 35 秒，未被维护重新启动。Host 正常退出约 62.42 ms，最后一代截图和 OCR 进程均已退出。新进程仍需要加载模型，立即恢复不能消除异常刚发生时的加载成本。

另外，原生截图入口在私有桌面完成 100 次连续选区测试：准备后的首帧为 52.65–67.71 ms，中位数 57.83 ms，样本 P95 为 66.58 ms；闲置 65 秒后首帧为 54.85 ms。每轮关闭后没有保留截图窗口。该轮测试进程的私有内存由 21.91 MiB 增到 56.32 MiB，句柄由 549 增到 551；这组数据记录连续创建窗口的开销，不作为长期内存稳定的结论。
