# 闪聊开源替代可行性方案

日期：2026-11-09（Asia/Shanghai）。状态：**调研完成，等待审阅；未实施替换，未证明候选项目在用户网络中可用。**

## 1. 结论与用户约束

**建议把 SimpleX Chat 列为第一验证候选，Jami 列为备选。现在不直接替换正式闪聊。** SimpleX 的文字消息经公共中转传递，不要求双方完成点对点打洞，更符合这次解决外网聊天失败的目标。它仍有包体、邀请方式、消息保存和文件上限方面的差异，必须先验证并由用户审阅，不能称为无损替代。

用户本次明确要求：

- 寻找成熟、开源、相似的项目，先交付可行性方案并保存文档。
- **必须无账号、无自建服务器。** 不提出购买服务器、注册第三方聊天账号或申请 TURN 服务账号作为使用前提。
- 本轮只调查和写方案，不替换产品代码，不安装候选程序，不修改真实 WinOne 配置和正式安装器。

本方案对“无账号”的工作解释是：不要求手机号、邮箱、服务端注册、登录或购买身份；加密密钥和昵称可由本机创建。SimpleX 的本地资料、Jami 的本地密钥身份都需要设备保存，不能宣传为“设备上没有任何身份或数据”。这个解释是方案假设，不额外视为用户已经接受持久保存聊天记录。

“无自建服务器”允许使用项目提供的公共服务，但不等于通信完全没有服务器。免费公共服务存在可达性、限额和运营变化；本方案不承诺所有网络下必连，也不把代码开源等同于公共服务有可用性保证。[S1][S2][S9]

## 4. 为什么优先验证 SimpleX

### 4.1 与本次故障的直接关系

当前闪聊先经 tracker 找到对方，再尝试 WebRTC 直连；缺少默认 TURN 时，双方发现也可能始终无法聊天。

建议方案让两端的 SimpleX 核心分别主动连接公共消息中转，由中转交付密文。文字消息不要求双方建立点对点 UDP 通道。这是降低当前 NAT/UDP 风险的**架构推断**，并非本次已经测得的成功率。语音／视频使用另一条 WebRTC 路径，不能把文字结论扩展到通话。[S1][S2][S6]

当前核心支持公共服务端口选择及 SOCKS 代理。**TCP 443 上的 SMP 不等于 HTTPS**；只允许网页流量的网络仍可能阻断它。应分别检查直连、现有代理、TUN，而不能宣传“用 443 就一定能用”。[S6]

### 4.2 有可核查的交付与安全记录

- 已发布 Windows CLI 和桌面安装包，核心不是只能运行在开发机的示例。[S3]
- 有群聊、私聊、邀请、文件与消息状态 API，存在复用完整聊天核心的路径。[S4]
- 官方公开了 2022 年实现评估和 2024 年协议设计评估的说明与报告入口。历史评估不覆盖全部 v7.1.2 代码，更不代表不存在漏洞。[S7]
- 官方明确公共服务器按尽力服务提供，没有 SLA；不把宣传中的历史在线率移植成 WinOne 的保证。[S1]

### 4.3 明确代价

| 项目 | 已查到的差异 | 处理原则 |
| --- | --- | --- |

## 5. 建议接入边界

### 5.1 推荐结构

保留 WinOne 的闪聊页面与交互外壳。聊天协议、密钥、消息队列和文件协议复用官方核心，放入按需启动的独立进程，由 WinOne 的现有进程管理负责启停。设置窗口与用户流程仍由 WinOne 统一呈现。

**优先评估官方 Node.js 库＋原生 `libsimplex`。** 官方已将它作为旧 TypeScript 客户端的替代，具有高层 API 和底层核心接口。核对能否复用仓库已有运行时；在没有检查版本、动态库与资源增量前，不承诺复用成功。[S4]

官方库会在首次使用时下载原生库到用户缓存。WinOne 应在构建／模块准备阶段固定版本、核对哈希并准备资产，使用上游支持的本地库路径；运行时不得偷偷下载、更新全局依赖或写入另一个 SimpleX 安装的目录。[S4]

首轮连通性对照可用官方 CLI，以分清“公共网络本身不通”还是“WinOne 适配出错”。CLI 当前仍有本地 WebSocket 控制接口，但不把旧客户端包当作新方案基础。锁定版本的 `Server.hs` 会输出收到的命令；所读连接处理未见令牌校验。若正式采用这一接口，必须补全核心控制入口的访问保护、来源检查与日志脱敏，不能只给外层桥接加认证就宣称已保护内部端口。[S15]

这两条是接入路径评估，不同时建设两套产品后端。验证后确定一条，淘汰另一条；不把简单替换扩大为通用聊天平台。

### 5.2 必须保留或明确审阅的功能

以当前源码和 2026-11-04 后的行为为准，不能只照 2026-11-01 的旧功能表。旧表中的“离页即退出”和“文件依赖 Tailcat”已经过时。

| 当前能力 | 替换验收要求 | 当前判断 |
| --- | --- | --- |
| 无注册、个人昵称、创建和加入 | 本地生成资料；创建、复制邀请、加入全链路真实执行；不引入账号登录 | 原理可行；未验证 |
| 房间号＋密码、旧房间互通 | 新旧链接明确区分；旧协议不能冒充新协议；活跃旧房间需有明确退出／迁移提示 | **不兼容差异，待审阅** |
| 群聊与群成员间私聊、成员列表、昵称同步 | 群聊与私聊严格隔离；切换会话不丢消息或草稿 | 核心有对应能力，映射待验证 |
| 端到端加密、身份校验 | 使用上游密钥与校验方式；旧“已验证”不得直接映射成现实身份已可信 | 机制不同，需准确文案和验收 |
| 晚加入者最近 150 条群聊历史 | 核查上游历史分享、成员权限和条数规则，不能默认新成员自动拥有旧历史 | 等价性待验证，不承诺已支持 |
| 正在输入、Markdown、代码复制、时间与作者 | 逐项核查上游事件和本地显示；没有等价事件时列缺口，不发送伪消息模拟 | 待验证 |
| Enter 发送、Shift+Enter 换行、中文组字、草稿和滚动保护 | 保留现有原生交互，真实窗口测试 | 页面可复用；未验证 |
| 文件选择、拖放、进度、取消、保存路径、文件名清洗和冲突处理 | 在同一闪聊入口完成；校验文件哈希；失败可恢复且不误报送达 | API 可评估；8 GiB 差异未解决 |
| 切到其他页面保持房间、关闭窗口退出 | 保留 `core.Keeper`／`SetAside` 语义；退出进程回收；不偷偷常驻 | 必须纳入生命周期验证 |
| 临时会话、重开行为 | 明确本地历史、密钥、未送达队列和服务器密文保留；关闭窗口不等于从他人设备删除 | **持久化差异，待审阅** |
| 中英、深浅主题、宽窄窗、离开保护和可关闭错误提示 | 沿用现有 UI；连接中、已连接、已发送、已送达、失败分别有真实依据 | 待验证 |
| 网络设置与错误诊断 | 用候选核心支持的服务器、代理与连接状态替代 tracker/RTC 字段；不静默丢弃旧配置 | 配置迁移待验证 |

选定上游版本后还须建立完整的“上游能力／配置／便捷操作 → WinOne 入口 → 实际验证”表。上表是现有闪聊的保底清单，不是削减上游功能的授权。上游的联系人、群管理、历史、文件、隐私设置等能力必须盘点；需要改变或缩小范围时，单列差异交由用户审阅。

### 5.3 许可与维护

- WinOne 当前根许可证为 GPLv3；SimpleX 核心和库为 AGPLv3，Jami 为 GPLv3-or-later。首次接入按仓库约定核查对应版本、传递依赖、修改与组合分发要求，不能凭“独立进程”自动判定没有其他义务。[S1][S9]
- SimpleX 的名称、Logo 与部分图形资产另有条款。优先沿用 WinOne 自有界面和图标，保留必要归属说明，不把源码许可扩展到品牌资产。[S1]
- 接入时同步 `third_party/`、许可证全文、来源摘要与 `THIRD-PARTY-NOTICES.md`。本轮未导入第三方源码或二进制，因此不伪造已接入清单。
- 上游更新先查发布说明、API 与数据迁移。数据库升级后不能直接用旧核心打开新库来“回滚”；保留兼容版本和升级前备份，并验证恢复。

## 6. 分阶段验证与停止条件

这些是审阅后的实施建议，本轮没有执行。时间是单人投入估算，不是承诺；真实异网设备和用户审阅的等待时间另计。

| 阶段 | 具体工作 | 交付与通过条件 | 估算 |
| --- | --- | --- | --- |
| A：先证明网络与核心可用 | 仓库内隔离运行官方 Windows 核心；第二台设备用新 WinOne 原型或官方手机客户端；仅测试双方自有身份；核对默认中转、版本组合和许可 | 跨网络文字、群聊、私聊、文件证据；进程组内存／CPU／启动／包体；功能差异表。失败则停止接入，不先重做 UI | 1–3 工作日 |

### 网络与行为验收矩阵

以下是建议门槛，**不是已经取得的测试结果**。至少覆盖两台物理设备、两个独立外网；两个本机进程、同一 Wi-Fi 和端口探测不能代替。

| 场景 | 应观察的结果 |
| --- | --- |
| 家庭宽带 ↔ 手机移动网络；不同运营商 | 每场景新建 10 次会话；10/10 在 30 秒内进入可通信状态；普通在线文字延迟 P95 ≤3 秒，超限保留原因与重测记录 |
| 双方均在 NAT 后；测试环境禁止 UDP、仅允许必要 TCP 出站 | 文字和文件仍可用；记录实际协议与端口。若是只允许 HTTPS 的网络，单独标注并验证，不混在 TCP 443 结果里 |
| 直连、用户现有 TUN、用户明确配置的代理 | 分别核查 DNS、路由与通信；不关闭或修改用户真实代理来制造成功 |
| 同一场景连续双向发送 100 条带序号消息 | 无丢失、无重复、会话归属正确；私聊内容不出现在群聊；显示“已送达”必须有真实回执 |
| 断网 60 秒、网络切换、睡眠后恢复 | 恢复连接后 30 秒内重连或明确失败；待发送消息无假成功，重试不重复 |
| 第二端离线，随后上线 | 明确队列和保留规则；区分服务器接收与对方收到；若临时会话已销毁，按已批准规则说明结果 |
| 3 人群聊、晚加入、成员退出、改昵称 | 历史与权限正确；群聊／私聊不会串线；断开后状态不冒充在线 |
| 文本、小图、100 MiB 文件及批准的上限边界 | 哈希一致；保存、重名、取消、断点／重试表现有记录；额外验证超过额度的明确提示 |
| 服务地址不可达、限流、凭据或密钥错误 | 分别报告失败；不跳过证书核对；不暗中退回明文聊天或永久挂在“正在连接” |

性能记录必须测完整进程组。模块未使用时不常驻；关闭后回收 Worker、连接和句柄。首轮实测后才确定新核心的正式资源预算，不能用官方 CLI 文件大小代替实际内存，也不能通过后台预热美化启动数据。

**停止条件：** 公共服务在目标网络不可达；官方核心版本无法配套；关键现有能力没有等价路径且用户不接受差异；资源增量不可接受；许可证或服务使用条件无法满足。出现任一条件，不把候选包覆盖到正式安装器。SimpleX 不通过时，再对 Jami 执行同一矩阵；两者都不通过则如实报告当前约束下尚无合格方案。

## 7. 审阅时需要确定的取舍

“无账号、无自建服务器”已经确定，不再重复询问。开始替换前还需要确认：

1. 是否接受邀请链接／二维码，以及手机端使用官方客户端；若必须纯网页即开即聊，SimpleX 目前不作为合格替代。
2. 是否必须保持临时会话、不保存聊天记录；若必须，先证明核心的临时资料、退出和异常恢复能满足语义。
3. 是否必须原样保留 8 GiB 文件；若必须，SimpleX 的默认公共 XFTP 路径不合格，须找到经批准的等价路径或改选候选，不能直接降为 1 GB。
4. 是否接受原型实测得到的包体与资源增量。148.04 MiB 只是当前 Windows CLI 资产参考，不先设为可接受成本。

建议先批准阶段 A 的隔离验证，再根据结果决定替换。**截至本文交付，没有可依据的异网聊天成功数据，也没有已完成的正式替换。**
