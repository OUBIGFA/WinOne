# 程序管理核查与上游同步（2026-11-08）

## BuddySwitch 现象与原因

“托盘图标收纳”和“启动后收起窗口”是两条执行路径。用户日志中，BuddySwitch 的图标已经进入收纳器，未完成的是主窗口收起。

- 当日 18:27:52.192：计划任务报告启动完成；18:27:52.486：程序管理观察到进程并进入现有进程处理；18:28:08.828：收到原生托盘图标。两项时间相差约 16.3 秒。
- 当时保存的窗口等待上限是 10 秒，收起前等待为 0 秒。该次等待期间没有匹配窗口的日志。原 `manageRunning` 在等待耗尽后，只要进程仍在，就返回 `Managed:true / already_running_skipped`，因此自动启动队列没有报告收起未完成。
- 上次接入的 DC 渲染兼容、窗口枚举锁修复和托盘就绪等待均仍在。`startup_visibility_windows.go` 与当前上游一致；这些修复不改变用户配置的窗口等待上限。
- 经用户授权实际启动一次 BuddySwitch：约 1.43 秒匹配到 `Tauri Window`；Esc 没有收起，原生关闭请求约 2.39 秒完成；3 秒内验证进程仍存活、窗口隐藏、同一窗口能够恢复。测试结束后由用户正常退出，确认无进程遗留。

**判断边界：** 历史日志记录了托盘注册时间，没有记录首个窗口出现的准确时刻；本次快速启动未复现当时的慢启动。结合“等待期间无候选窗口”、超时误报的真实窗口回归与实际原生收起成功，当前证据支持窗口就绪超过 10 秒而被漏处理，不能把托盘注册时间直接当作窗口出现时间。

使用建议：在程序管理设置中把“窗口等待上限”从 10 秒调至 30 秒，再观察登录时的慢启动。该设置影响所有程序；用户明确选择保留 10 秒并自行调整，本次未改真实配置。保留 0–120 秒的原有范围，不对 BuddySwitch 硬编码、不偷偷延长已有配置。

## 本地修复与验证

| 场景 | 行为与证据 |
| --- | --- |
| 现有进程的窗口迟于等待上限出现 | 自动收起返回未完成并记录警告；`TestTaskStartedLateWindowReportsUnfinishedDismissal` 修复前失败、修复后通过；同一进程就绪后重试可原生收起 |
| 窗口在配置时限内迟到 | `TestLateWindowWithinConfiguredWaitClosesNatively` 验证原生收起、进程保留、样式释放 |
| 程序本来已隐藏到托盘 | 只在观察到该程序的窗口均已隐藏时保留成功状态；`TestAlreadyHiddenNativeWindowIsNotADismissalFailure` 先失败后通过 |
| 主窗口收起但另一窗口拒绝 | 不把隐藏的主窗口当作全部成功；`TestAlreadyRunningPartialDismissalIsNotHiddenSuccess` 验证剩余窗口仍可操作 |
| 查询计划任务时删除/重建任务 | 上游同进程回归修复前在第 2 轮失败，接入后通过；只使用唯一命名的测试任务 |
| Host 与 Worker 分处两个进程 | 直接照搬上游进程锁仍失败；新增跨进程回归确认。两边现在共用 `internal/logintask.RunSchtasks`，用当前用户、当前会话的 Windows 互斥对象串行执行；两种并发回归通过 |

共享计划任务入口保留原有权限、参数、OEM 错误解码和无控制台启动。Windows 互斥对象按当前用户限制访问，并允许同一用户的普通/管理员进程共同使用；等待失败明确返回错误。它协调本产品的命令，不宣称能够阻止外部软件同时修改系统任务。
