# 架构与性能约定

仅在任务涉及服务边界、技术路线、性能预算和完整流程验收时读取。本文件承接原项目 AGENTS.md 的约定，不改变需求。较新的明确约定优先；历史计划中的“当前顺序”须结合相关开发状态核对。

- 用户于 2026-10-10 明确要求：以后指定复用的功能一律全量接入，禁止 Agent 自作主张精简。先查明指定版本的完整功能、配置项、便捷操作与执行路径，建立“上游能力 → WinOne 入口与实现 → 验证证据”对照。不得只挑容易实现或已有测试覆盖的部分，不得以“够用”“最小实现”“轻量化”替代要求。
- 技术适配可以替换宿主接口、统一 UI、语言和配置，但必须保留功能语义、可操作入口及真实执行。删除上游功能、缩小适用范围、隐藏选项或用静态占位代替执行，均须先说明具体差异并取得用户明确授权；已有完整接入要求不是精简授权。
- 发现曾被精简的复用功能时，应恢复遗漏内容并补齐验证。环境、依赖、账号或权限使某项暂时无法验证时，明确标记未完成及所需条件，继续完成独立部分；不得省去该项后宣称全量完成。

- 性能是技术选型与实现顺序的首要考虑。先定义预算、测量同负载原型，再铺开实现；交付必须验证完整进程组的冷/热启动、输入响应、CPU、内存、句柄、包体及退出回收。原生控件不自动等于性能达标；预算按用户最新明确要求执行，不以隐藏常驻、预热或减少功能掩盖成本。
- 用户于 2026-10-08 明确接受 Host 约 43 MiB 的私有工作集，要求灵活判断并优先尽快完成正式版。原 40 MiB 不再作为阻断发布的硬门槛；当前自动检查参考 43 MiB，少量波动结合稳定性、持续增长、CPU 和退出回收判断，不为数 MiB 的微调反复拖延。优先完成既定功能、安装更新、配置保护和完整使用流程，非阻断微调留待后续。
- 禁止在已被实际体验否定的方案上堆叠补丁。先查明根因并对照成熟实现，必要时替换完整流程；不得用延时、过渡画面、硬编码补偿或放宽指标掩盖问题。原型通过不等于产品通过，未完成完整流程验收不得替换交付包或宣称修复。
- 按 `docs/WinOne架构与开发计划.md` 实施；状态写入 `docs/development.md`，不将未验证功能标为完成。
- 项目核心：接入模块的能力，由 WinOne 统一设置、调用和呈现。上游独立设置窗口、编辑器或工具栏不作为最终产品界面；截图全流程也必须统一设计。
- 采用“想三步做一步”：每个可交付阶段实施前明确当前与后两步的接口、依赖和验收，完成后滚动规划后三步。模块管理、配置、安装更新、双语和性能先有共同路线，不能逐模块临时拼接。
- 涉及交互、用户习惯、安全、安装更新等专业判断，先查权威资料和成熟实现，记录来源及适用范围；不把个人推断、组件宣传或单项测试当作验证结论。
- 轻量是验收约束：测量 Host、共享原生UI宿主、全部 Worker 及运行时辅助进程，迁移期间也计入 WebView2 进程；禁用模块不常驻、不轮询。默认开启“保持界面后台运行”，关闭窗口后保留同一界面进程与窗口以便快速唤起；关闭此设置后，关闭窗口释放无任务的界面资源。保留未保存修改与运行中任务保护；托盘退出、权限重启与 Host 正常退出仍关闭界面进程。新模块必须提交资源增量和退出回收证据，不能只测主进程。

实现资料按需选择：[WinOne架构与开发计划](../WinOne架构与开发计划.md)、[performance-baseline](../performance-baseline.md)。不要递归展开全部链接。
